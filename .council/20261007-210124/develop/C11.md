## C11 Bench ledger: tokens per correct answer against a random arm

## The concept

One table, `bench/ledger.csv` (plus a printed view), that decides every EmbeddingGemma 2 proposal before it is built and prunes it after. Each candidate (veto, k-center budget, narration demotion, cluster sheets, medoid frames, audio tower, even the existing heuristics) is a row. Each row is run as three arms on the same QA questions at equal image count and equal image tokens: the feature, the current heuristic, and uniform-random frames. The answers are compared per question (paired), and the headline number is image tokens per correct answer, with a sign test against random.

What makes it surprising, and what to keep:
- The model's own proxies (cosine, drop rate) never count as evidence. They are cheap pre-tests. A pre-test that passes while the headline row does not move is logged as a false positive, so the ledger also learns how far to trust each proxy (m01.r2.1).
- The ledger prunes as well as promotes. A feature that ties random gets a generated deletion diff (m03.r2.1). The bench proposes removing code.
- A ceiling arm (text only: storyboard plus transcript, no images) gives, per video, the largest gain any selection idea could earn (m02.r2.5). A feature chasing a gap under noise is dead before it is built.
- Verdicts are written before runs (kill numbers), and the file is the repo's memory: a "graveyard" row records why a feature died, so a new model release does not reopen it (m02.r2.6, m03.r2.5).

Who it is for: Sam, deciding which of the five already-proposed ideas plus the council's extras are worth their maintenance cost. Second reader: any later agent that wants to know "have we observed this?" The ledger is the answer.

Honest scope note: this is not an EmbeddingGemma 2 feature. It is the instrument that says whether any use of the model earns its place. That is also why it is the cheapest way to "extend usage": it makes the extension decisions on measured answers, not on cosine plots.

## How it works

Existing base (checked in the repo): `bench/prep_qa.py` already builds per-video folders: `oracle/` (dense frames for the question writer), `A/` transcript only, `B/` transcript plus N uniform frames, `C/` framesift storyboard plus sheets, `D/` C plus meaning.md. `bench/evaluate.py` already reports coverage against uniform at equal N and image tokens. What is missing: the questions, the answer-and-grade loop, the random arm with seeds, and the paired statistics. The README of `research/261002-architecture.md` already names "QA eval harness, about 15 questions per video type" as the first build item, and says the headline metric should become correct answers per agent token. C11 is that item, made rigorous.

Rows and arms:
1. Fixed question set: about 15 per video, 4 videos (animation, lecture, 100 s explainer, short film), about 60 items. Questions are written from the `oracle/` dense sheets by a separate pass, tagged by need: `needs-image`, `speech-answers-it`, `needs-two-frames` (m02.r1.1: two frames are "different" if a question needs both, which gives the same/different pairs for the layout-collapse gate with no extra hand labelling).
2. Arms per feature row, equal image count N and equal tokens (image dimensions held fixed, so tokens match; use the Claude vision docs' formula and note that `evaluate.py` still uses width*height/750 while current docs describe 28x28 patches, so recompute tokens once from the API usage field rather than the formula):
   - feature arm (e.g. veto on, k-center chosen frames),
   - current heuristic arm (today's keyframes),
   - uniform-random arm: K seeds (start with 3) of random frames at the same N,
   - null arm: random vs random with two different seeds. Its win/loss spread is the noise floor of the whole setup.
   - ceiling arm (once per video): text only.
3. The agent answers each question from the arm's folder only (same as the C/B folders). Temperature 0, one fixed model and prompt, answers logged to JSONL with the arm, seed, question id, tokens read.
4. Grading: exact/short-answer rubric written with the question; a judge call only for free text, with the rubric, and a 10 percent human spot check.
5. Statistics, per feature versus random and versus heuristic: count discordant pairs (feature right and random wrong, and the reverse), exact binomial sign test. Pairing removes question difficulty from the variance (Miller, "Adding Error Bars to Evals", recommends paired differences and clustered standard errors). Report the column `beats random: yes / tie / no` and `tokens per correct answer`. Rule: with about 60 items most pairs tie, so a verdict needs roughly 8 of 10 discordant pairs on one side; below that the row says "undecided", never "works".
6. Pre-test column (cheap, from the embed cache): MRL recall, embedding-to-pixel ratio, instance pairs, cosine drop rate. Order of work follows the pre-test table, and each pre-test has a kill number written first (m01.r1.6).
7. Drift pin (m01.8): per video, mean pairwise cosine and veto drop rate are stored in the ledger; a later commit moving them beyond a margin fails the bench. It is an alarm, not evidence of quality.
8. Outcome log (m01.r2.4): every run appends threshold, `check` holes, and QA correctness to a CSV. Over time this is a labelled table for threshold audits (veto, merge, demote), replacing a hand-labelled pair sheet. Compare codec-calibrated threshold versus outcome-best threshold per video.
9. Whole-video row (m03.r2.6): last, the agent writes a summary from sheets plus storyboard; graded on the QA items answerable from it. This covers the user's full chain (find, grid, send, analyse) so a feature that lifts frame scores but not the summary is flagged "outside the ask".
10. Run file layout: one `bench/ledger.py` that reads rows from `bench/ledger.toml` (claim, purpose in {find, grid, send, analyse}, cache needed, kill number, status). A row marked passed with no recorded number fails the bench (m01.r2.6).

Where the model is used: a single script embeds 1 fps frames of the 4 videos at 768 dims and caches them (`bench/cache/*.npy`); MRL truncations are slices of that cache. Nothing goes into the product until a row passes.

## First move

This week, in order, each step standalone:
1. `bench/embed_cache.py`: decode 1 fps frames for the 4 sample videos (about 20 minutes of material in total, a few thousand frames), embed with EmbeddingGemma 2 through sentence-transformers or MLX, save float16 768-d arrays. This also settles the unknown "throughput on an Apple Silicon Mac". Stop condition: if the vision tower is far slower than about 2 to 5 frames per second, record it and switch to a 0.5 fps cache.
2. Write the questions for the shortest video first (python_100s): 15 questions with tags and rubric, from the existing `oracle/` sheets. Run `prep_qa.py` conditions A, B, C once and answer them. This produces the first real number the repo has ever had for transcript-only vs uniform vs framesift, and the first noise estimate (run B twice with different seeds).
3. Read off the ceiling: if A (text only) already answers nearly everything on a video, selection ideas cannot pay on it, and the ledger says so on day one.
4. Only then add the random and null arms and the sign-test printout.

Do not build the ablation-diff generator, drift pin or outcome CSV in week one. They are cheap once the arms run.

## What must be true, and the cheapest test

1. The QA set can discriminate. If transcript-only and uniform both score at ceiling, or all arms tie, the bench cannot see differences and the whole ledger is decoration. Test: step 3 above, one hour. Mitigation: write `needs-image` questions on purpose (what is on the slide, what changed between two shots); animation and short film are the most visual.
2. The agent answers deterministically enough. Test: run the null arm (random vs random, different seeds) and the same arm twice. If the null arm shows more than a few discordant pairs, the noise floor is too high for 60 items, and the set must grow or answers must be sampled several times.
3. 60 items give enough power. Quick check: a discordant count of 8 to 1 gives p about 0.02 one-sided; 6 to 3 does not. If real features move fewer than 8 or so items, say so ("below what this bench can see") and fall back on a larger set or on pre-test evidence, written as such.
4. Random really is a fair opponent: same N, same sheet layout, same image size, same timestamps labels. Otherwise the arm differs in layout, not selection.
5. Generated questions do not leak the selection method. Questions come from the dense oracle, never from the keyframes of any arm.
6. Tokens per correct answer is not gamed by answer length; count image tokens only, as already defined in `evaluate.py` (text is equal across arms).
7. Judge reliability: spot check 10 percent by hand; disagreements above about 10 percent mean rubrics are too loose.

Cheapest overall test: steps 1 to 3 above, a day of work, and about 15 questions times 3 conditions of agent calls. If step 3 shows A already ceiling on three of four videos, kill the strong claim and keep only the pre-tests and the drift pin.

## Prior art (with URLs)

Close, and the reason this is not new:
- Otani et al., "Rethinking the Evaluation of Video Summaries" (CVPR 2019): random summaries matched or beat state of the art on SumMe and TVSum, so F1 comparisons were misleading. Same logic as the random arm. https://arxiv.org/abs/1903.11328 and https://mayu-ot.github.io/rethinking-evaluation-of-video-summaries/
- Adaptive Keyframe Sampling (AKS) and AdaRD-key treat uniform sampling as the baseline that keyframe selectors must beat on video QA, and report accuracy gains over it. They run it on public benchmarks with fixed frame budgets, not on one tool's own pipeline features, and they do not report tokens per correct answer or deletion of features. https://arxiv.org/abs/2502.21271 , https://arxiv.org/html/2510.02778v1 , FOCUS (ICLR 2026) https://github.com/NUS-HPC-AI-Lab/FOCUS
- Miller, "Adding Error Bars to Evals" (2024): paired differences, clustered errors, power analysis for LLM evals. This supplies the statistics; a sign test is the simple version. https://arxiv.org/abs/2411.00640
- Claude vision token arithmetic: docs describe 28x28 patches, third-party pages quote width*height/750; verify against the API usage field. https://platform.claude.com/docs/en/build-with-claude/vision

What is still different: a per-feature ledger inside one small tool, with an equal-token random arm, a null arm for noise, a text-only ceiling, false-positive tracking of proxies, and deletion diffs when a feature ties random. I found no project doing this inside a video-to-agent preprocessing tool; I did not search exhaustively (a handful of queries), so treat "none found" as modest evidence.

## What it costs to run

- Infra: no new service. Embedding runs locally once per video (cache on disk, a few thousand 768-d vectors is a few MB per video; half-precision halves that). Agent calls are the real meter: each row means roughly 5 arms times about 60 questions of model calls with images. I did not measure this. A sheet-set read per question is on the order of 10k to 30k tokens, so a full-row run could reach a few million tokens; mitigate by putting all of a video's questions in one context per arm (about 15x cheaper) and by running full rows only for features that passed their pre-test.
- Operational: nothing runs in CI by default; it is a command Sam runs when deciding. The drift pin is the only part that runs often, and it needs only the cached embeddings (no agent calls).
- Maintenance: one script, one TOML of rows, one CSV, a question file per video. The ledger deletes more than it adds if it works: every row that ties random removes a feature and its knobs. The main risk is staleness: questions and rubrics must be revised when a video changes; with four fixed samples that is nearly zero. A second risk is overfitting to 60 questions on 4 videos: keep a held-out video added later and never tune on it.
- Development: low (build effort is not the constraint).

Runs: nothing new running; one local bench script, a model call budget per decision, and the cached embeddings on disk.
