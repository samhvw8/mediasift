## C05 Ask-conditioned sheets with a coverage floor and ready-made queries

## The concept
Today "best frames" has no referent: sheets are 12 consecutive keyframes (`render.contact_sheets` chunks `PER_SHEET=12` in time order). C05 gives the agent one optional lever and one menu.

- `framesift analyze video.mp4` (no question) works as now, but each sheet gets a footer of **ready-made queries**: for each cluster of stored frame vectors, the 2-3 transcript phrases nearest the cluster centre, printed copy-paste ready, e.g. `ask: "the loss curve slide"`.
- `framesift sheets <out> --ask "why does the build fail?"` re-lays-out the sheets from stored vectors in milliseconds. The question is embedded once; each segment keeps a **floor of one cell** (its most central keyframe), and the remaining cell budget goes to the frames nearest the question. Output is the same `sheet_NN.jpg` set, with a relevant-first ordering and a printed line saying which segments were floor-only ("S04, S07 shown as floor only, nothing matched").

What stays surprising: the question is a *layout input*, not a lookup (this makes `find` a mode of the default output rather than a second command), and the menu removes the cold-start problem (the agent does not have to know what to ask; the second pass starts from copying one line). The floor is the fix for the obvious failure of goal-conditioned views: a wrong question must not hide the answer.

Who it is for: the coding agent (Claude Code and similar) reading a video it knows nothing about, then following up. Not for a human browsing.

## How it works
1. **Stored vectors.** At analyze time embed each keyframe (vision tower) and each transcript window (text tower), store both in `signals.npz` (already proposed item 5; numpy brute force).
2. **Dimension: store 256, not 128.** The parent ideas (m03.r1.4, m02.r2.3) said 128 dims. The model card says 128d "degrades multimodal quality substantially" (MMEB v2 59.01 at 768d, 56.24 at 256d, 45.65 at 128d) and must be validated first; 256d is "close to lossless". A few thousand vectors at 256 float32 is about 3 MB; re-ask cost is still sub-millisecond. Always re-normalise after truncation, and query and corpus must share the dimension (both from the card). So: 256 by default, 128 only if the bench says it holds.
3. **Cell budget.** Keep the existing budget (`--max-frames` or segment count). Floor: 1 cell per segment, chosen as the frame closest to the segment's mean vector. Remaining cells: rank all other keyframes by `cos(q, v)` and fill, but apply a greedy diversity rule (MMR-style: skip a candidate whose cosine to an already-chosen frame exceeds a cut) so five near-identical frames of one slide do not take five cells. This is the relevance-plus-coverage trade AKS formalises.
4. **Order.** Sheet 1 holds the best relevance cells; later sheets hold the floor and the remainder, in time order. Labels stay `S04 12.3s` and add the score, e.g. `S04 12.3s q0.61`, so the agent can tell a strong match from a floor filler.
5. **Weak-match honesty.** If the top score is not above the video's own background (for example below the 90th percentile of all frame-to-question scores for random control phrases), print "no strong match; showing coverage layout" instead of pretending. Crashing beats corrupting.
6. **Menu.** k-means (k about sheet count, or one per ~3 segments) on the 256-d frame vectors; for each centre take the nearest transcript-window vectors and print the text, plus the timestamp span. If there is no speech, fall back to the nearest VLM caption if `meaning` ran, else print the cluster's timestamps only and say there is no text handle (the shared space also lets a *frame* be the query, but that is a later step).
7. Plain-text question embedded with the model's query prefix (card: task instruction prefixes); the text tower is the 270M part, loaded without the vision/audio encoders for this call (selective encoder loading is a documented feature).

## First move
This week, no CLI work: write `bench/ask_probe.py` that loads the 4 sample videos' existing keyframes, embeds them and the existing transcripts with EmbeddingGemma 2 via sentence-transformers at 768/256/128, and for each `bench/prep_qa.py` question: (a) builds the sheet set the C05 way, (b) builds the current chronological sheets, (c) builds a random-frames sheet set at equal cell count. Print per video: does the QA-evidence frame land on sheet 1 (hit@1 sheet), at each dimension. That is a day of work and answers the whole concept.

## What must be true, and the cheapest test
1. **Text question to frame retrieval works well enough** on screen recordings, slides and animation, in English (Vietnamese unknown). Test: hit@1-sheet and hit@3-cells on the QA evidence frames, per dimension, vs random. Kill if not clearly above random on at least the lecture and explainer samples.
2. **256d (or 128d) holds up on this workload.** Test: same run; require 256d within a point or two of 768d. If only 768d works, storage grows to about 12 MB per video, still acceptable, but say so.
3. **The floor actually prevents blinding.** Test: ask a deliberately wrong question for each QA item; accuracy with floor must be no worse than chronological sheets at equal cell count (the downside bound). Without the floor it should be visibly worse, which shows the floor earns its place.
4. **Tokens per correct answer drops.** The metric from the council's bench ideas (m03.8, m02.r1.1): three arms (C05 with the true question, current, random) at equal image count; the value is correct answers per 1k image tokens, plus a "beats random" column.
5. **Menu phrases are useful.** Test: for each QA item, does any printed menu line, used as `--ask`, put the evidence on sheet 1? Report the fraction. If that is low, drop the menu and keep `--ask` only; if high, the menu replaces most typed questions.
6. **Layout is not collapsed.** Per the earlier research, semantic embedders score about 20 on instance retrieval (SigLIP2) vs DINOv2 about 51: two slides with different numbers may embed together. The MMR dedupe cut can then wrongly drop a frame. Test: on the lecture sample count dropped pairs that the pixel stats call different slides; if material, make the cut conservative or take the dedupe from pixel drift, not embeddings.
7. **Does the agent actually use it?** The second pass only happens if SKILL.md tells the agent to; check in the skill and watch two real runs.

## Prior art (with URLs)
Something close exists; the core mechanism (question-conditioned frame selection balancing relevance and coverage) is not new.
- **Adaptive Keyframe Sampling (AKS), CVPR 2025**: selects frames by a trade-off of prompt relevance and video coverage to fit a token budget, improving long-video QA. https://arxiv.org/abs/2502.21271 , code https://github.com/ncTimTang/AKS . It is the same relevance-plus-coverage idea. Different here: AKS targets a model's input tokens inside one pipeline; C05 is a CLI whose output is images and markdown for an *external* agent, keeps a hard one-per-segment floor, reports floor-only segments, and re-asks from stored vectors.
- **Query-adaptive token selection for video QA** https://arxiv.org/abs/2504.21403 , plus recent query-aware keyframe papers (REAP, CRAFT, VSI https://doi.org/10.48550/arxiv.2508.06869 which also uses subtitles). All are one-shot selection for a given question inside a research pipeline; none found shipping a menu of suggested questions.
- **Query suggestion / chapters in video search UIs**: the menu is the "show suggestions rather than wait for a typed query" pattern (my recollection of YouTube chapters and Vimeo search; not verified with a source). I found no tool that prints transcript-derived queries from visual clusters under contact sheets for an agent. The menu is the least-precedented part, and its value is the least certain.
- **EmbeddingGemma 2** facts used: MRL truncation table, the 128d warning, re-normalise rule, query prefixes and selective encoder loading: https://huggingface.co/google/embeddinggemma-2 ; announcement https://developers.googleblog.com/en/embeddinggemma-2-the-developer-guide/ .
- General MRL background: https://arxiv.org/abs/2205.13147 .
Not checked: whether text-query to frame retrieval quality of EmbeddingGemma 2 is good on screen-recording content (no benchmark found; this is test 1), and throughput on Apple Silicon (unknown).

## What it costs to run
- **Infra:** $0. Local model, no hosted service. Storage about 3 MB per video at 256d (about 1 MB at 128d). One-time model download (the model is about 1.5 GB in BF16 safetensors on HF; quantised versions are smaller).
- **Per-turn tokens:** the point of the concept. Sheets hold the same cell count as today, so image tokens do not rise; the menu is a few dozen text lines per sheet. Savings come from the agent seeing the relevant frames first and not needing a second pass over all sheets. Unproven until test 4.
- **Compute:** embedding every keyframe and transcript window once at analyze time (cost unknown on Apple Silicon; measure in the first move). Re-ask: milliseconds, text tower only for the question.
- **Operational:** nothing to watch; no daemon. Failure modes are loud: refuse if stored vectors are missing or the dimension mismatches the query (never silently compare 128 to 768), print "no strong match" instead of a fake ranking.
- **Maintenance:** knobs added are the diversity cut and the cluster count, both to be derived or fixed from the bench, not exposed. Versioning: vectors are tied to the model and dimension, so `signals.npz` must record both and re-embed on mismatch. The menu depends on speech; silent videos get no handles.
- **Runs:** adds one optional model dependency (EmbeddingGemma 2, local) and a vector block in `signals.npz`; nothing hosted, nothing scheduled.
