## Fragile assumptions

1. **About 60 questions on 4 videos can separate a feature from random frames. Shaky, probably false.**
   - The concept's own rule needs roughly 8 of 10 discordant pairs on one side. The other 50 items tie. A selection feature (veto, k-center, demotion) changes which frames the agent sees. It will flip a handful of answers, because most answers come from speech or from frames any selector keeps.
   - The expected outcome is that nearly every row reads "undecided". The ledger then neither promotes nor prunes. It also contradicts its own deletion rule, since "ties random" cannot be told apart from "bench too weak".
   - Otani et al. (https://arxiv.org/abs/1903.11328) found random summaries matching state of the art. That supports the random arm as an opponent. It also says the gap to detect is small.
   - Questions cluster by video (4 clusters), so the sign test's independence assumption is optimistic. Miller (https://arxiv.org/abs/2411.00640) recommends clustered errors for this reason. The concept cites the paper but then uses a plain binomial.
   - Status: untested. The concept's step 3 and the null arm test it cheaply.

2. **The text-only ceiling is low enough to leave room. Shaky.**
   - Public video-QA benchmarks are known to leak answers through language priors. See TVBench (https://arxiv.org/html/2410.07752v2) and the decomposition study (https://arxiv.org/html/2505.14321v1). Video-MME-v2 filters questions with a text-only model (https://arxiv.org/html/2604.05015v1).
   - Here the questions are written by an LLM from dense frames, and the agent gets the full transcript plus the storyboard. The sample set is lecture, explainer, animation and film, which are speech-heavy except the animation (Big Buck Bunny, no dialogue) and the film.
   - Likely result: three of four videos sit near ceiling on the text arm. The concept's own kill rule then removes most of the ledger.
   - If instead questions are forced to be `needs-image`, the question writer has chosen what is visually salient. That biases towards whatever the dense-frame writer finds notable, which may match one selector's bias.
   - Status: untested, and the cheapest test already exists in step 3.

3. **Answers from a harness agent are deterministic enough at the item level. Shaky.**
   - Temperature 0 does not give identical outputs for image-bearing calls. The null arm will show some discordance. With only about 10 discordant pairs needed for a verdict, noise of 3 to 5 flips swamps the signal.
   - Grading by an LLM judge with a 10 percent human spot check adds a second noise source. The judge is the same model family as the answerer, so correlated errors are likely.
   - Status: untested. The null arm measures it, but the fix is more samples, which is the cost problem below.

Smaller issues, all checkable:
- The concept says `evaluate.py` uses width*height/750 and should be recomputed from the API usage field. That is correct (`bench/evaluate.py` line 31 `tokens()` and its docstring). Equal image count at fixed size makes tokens equal anyway, so "tokens per correct answer" collapses to "correct answers at equal N". The headline metric adds nothing over accuracy until arms use different image counts.
- The concept says 4 sample videos. `bench/v01/` and `samples/` hold 5 (big_buck_bunny, cs50_lecture, python_100s, tears_of_steel, and a cancer entry in the bench JSON). Not an error in substance, but the first-move numbers should be recounted.
- Step 1 plans a cache of 1 fps embeddings for about 20 minutes of material. If the vision tower runs below the stated 2 to 5 frames per second, the fallback of 0.5 fps changes what the pre-tests see. Throughput is unknown (the brief says so).

## Pre-mortem

A year on, `bench/ledger.csv` has 3 rows with numbers and 8 marked "undecided". Week one went well: the python_100s questions were written and the text-only arm scored high, so the "needs-image" tag was added to force a gap. The uniform arm and framesift tied within noise. That was reported honestly and nobody objected.

Then the model calls became the meter. Each full row means roughly 5 arms across 60 questions with images. Sam ran two rows, saw "undecided", and stopped paying for the rest. The embedding-based features (veto, k-center) were built anyway on pre-test evidence, because the pre-test column is cheap and the headline column is not. The ledger therefore recorded "pre-test passed, headline undecided" for every feature, and the concept's false-positive logic never fired because it needs a decided headline.

New models arrived. Questions and rubrics stayed fixed on four videos, and the drift pin began failing whenever the embedding model or the tokenizer changed, so it was loosened and then ignored. The `ledger.toml` rows became stale documentation. Nothing failed loudly. The repo had an instrument that says "undecided", and a few features that shipped on proxies.

## Who loses

- **The embedding-based feature proposals (1 to 5).** They lose their easy path of "cosine looks right, ship it". The response is predictable: argue that the bench is too weak to count, and ship on pre-tests. That is the likely failure above. It is a process risk, not an opponent.
- **Sam's time and tokens.** The agent calls are the real running cost, and the concept's weighting of operational and infra cost says that matters most. The estimate of a few million tokens per full row is unmeasured by the concept's own admission.
- **Existing heuristics (keyframe-drift, codec-as-evidence).** The deletion-diff idea puts them at risk. They were tuned from decision notes, and a tie with random on 60 items would argue for deleting code on weak evidence. Defenders will point to the decisions in `.okf/decisions/`. Their response is right to resist when the verdict is merely a tie.

## Fixes

- **Underpowered bench.** Smallest change: do not claim a sign-test verdict below a pre-computed minimum detectable effect. Print the power for the observed discordance next to each row. Add one more video of each kind rather than more questions per video, because that breaks the clustering. Or no fix: with 60 items this bench can only see large effects, and that is the price. Say so at the top of the ledger.
- **Ceiling.** Run the text-only arm first (the concept's step 3) and let it drop videos, not just features. Write questions only after the text-only arm has failed them: keep an item only if the text-only arm gets it wrong. This is the Video-MME-v2 filter, applied to the question set. It is cheap and removes the leakage in assumption 2.
- **Noise.** Run each arm three times and take the majority per item, and report the null-arm discordance first. If the null arm shows more than about 3 discordant pairs, stop. No fix is possible without more items.
- **Cost.** One context per video per arm (the concept already proposes this), and a hard cap on calls per row written into `ledger.toml`. A row that exceeds it fails rather than silently running on. This fits "crashing beats corrupting".
- **Metric.** Hold N equal and report accuracy. Reserve "tokens per correct answer" for the comparison that actually varies N: the `--max-frames` budget (proposal 2). Otherwise drop the phrase.
- **Proxies without a decided headline.** Add a rule that a feature may ship on a pre-test only if it removes code or a knob, and never if it adds surface. That aligns the ledger with Sam's maintenance weighting.
- **Staleness.** No fix: this is the price of a fixed four-video set. A held-out video, as the concept suggests, is the mitigation.

## Verdict

**Survives with changes.**

The idea of testing each EmbeddingGemma 2 proposal against random frames, with a text-only ceiling, is sound and well grounded (Otani et al.; the text-only filters used by video-QA benchmarks). Its one conceptual problem is that it is a measuring tool, not a use of the model. The brief asked for uses that improve understanding per token, so it should be presented as the gate for the other proposals, which is how the concept already frames itself.

Changes needed before anyone builds it:
1. Make the text-only ceiling filter the question set, and keep an item only if text-only fails it.
2. Report the minimum detectable effect and the null-arm discordance first, and declare "undecided" the expected result for small features.
3. Use clustered or per-video analysis, not a plain pooled sign test.
4. Put a hard cap on model calls per row.
5. Hold N fixed and report accuracy. Use tokens per correct answer only where N varies.
6. Allow a feature to ship on pre-test evidence only when it deletes code or a knob.
