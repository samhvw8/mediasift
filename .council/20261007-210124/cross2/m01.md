## Builds
### m01.r2.1 Three whys applied to the whole ledger: the top-level test is "did the agent answer right, cheaply"
Builds on: m03.r1.2 + m02.r1.1 + m01.r1.2
Ask "for what purpose" of the tokens-per-correct-answer meter: to rank features (level 1), to decide what to delete (level 2), to prove the harness understood the video (level 3). Level 3 is the only one with a real referent, so the ledger gets one headline row: the agent, given only sheets plus storyboard, answers the QA set; every feature is scored by its effect on that row, not on its own proxy (cosine, drop rate). Proxies stay only as cheap pre-tests, and a pre-test that passes while the headline row does not move is recorded as a false positive, so the ledger also calibrates how far to trust each pre-test.
### m01.r2.2 The sentence-level redundancy probe, three levels up: from "frame vs speech" to "does the agent need the image at all"
Builds on: m01.r1.1 + m03.r1.1 + m03.1
Why score frame vs speech cosine? To demote cells. Why demote? To save image tokens. Why save them? Because the agent may answer without them. Test that top level directly: run the QA twice, once with every sheet and once with text only (storyboard plus transcript), and list the questions where the image was never needed. Those questions define the "speech already says it" class by outcome, and the cosine probe from r1.1 is judged on whether it predicts that class, not on a hand-labelled yes/no, which removes the labelling session.
### m01.r2.3 Local quality by purpose: each video type gets the job its evidence supports, chosen by a measured recurrence number
Builds on: m03.r1.5 + m02.r1.6 + m01.r1.4
Why cluster? To build return maps and cluster sheets. Why? To cut repeat images. Why? Only videos where shots recur have repeats to cut. So the manifest records a recurrence ratio (stored vectors falling into a cluster seen earlier / all keyframes) and the layout follows it: high on lecture and explainer gives cluster sheets and a return map, near zero on the short film and animation keeps chronological sheets. The out-of-distribution warning from m02.r1.6 reuses the same number, so one column serves layout choice and the "this video is unlike everything seen" alarm.
### m01.r2.4 Ten times larger: the harness's own final answer becomes the label for every threshold
Builds on: m03.r1.3 + m02.r1.3 + m01.r1.3
The check loop scores a summary against segments. Push it to the top purpose: thresholds (veto, merge, demote) have no ground truth except whether the agent's analysis was right. Keep a log of runs: threshold setting, `check` holes, unsupported claims, QA correctness where known. Over the bench this gives a labelled table that replaces the hand-labelled pair sheet for threshold audits, and the gap between the codec-calibrated threshold and the outcome-best threshold, per video, is published. No new running service; a CSV the bench appends to.
### m01.r2.5 Audio tower admission by observation, with the kill result written down in advance
Builds on: m03.r1.6 + m02.r1.5 + m01.r1.6
Why load the audio tower? For non-speech stretches. Why those? Because transcript and log-mel both say little there. Why does that matter? Only if the agent gets a question the sheets cannot answer. So the admission test is one number: on animation and short film, among QA items that fall in VAD-silent windows, how many does the harness get wrong with sheets and storyboard alone? If that count is zero or one, the tower is rejected and recorded with that count; if two or more, run it on those windows only and see whether those items flip. Both outcomes are written down before running, so neither can be argued after the fact.
### m01.r2.6 Fresh: a "cheapest claim first" run order that is itself a script
Builds on: m01.r1.6 + m03.r1.7
The requirement trace and the experiment order are two lists that can drift apart. Make one bench file with rows (claim, purpose it serves from the five-part goal, cache it needs, kill number, status). The embed-cache step runs first; any row whose purpose is not find, grid, send or analyse is flagged outside the ask; any row marked passed without a recorded number fails the bench. This makes "have we observed it?" a check the repo performs on itself.
