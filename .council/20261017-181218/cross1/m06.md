## Builds

### m06.r1.1 Hand-anchored glyph crops: native-resolution text only where the pointer or caret rests
Builds on: m03.4 + m06.8 + m06.1
m03.4 gives the agent's own eyes the dense text as native-resolution crops of each distinct text state; m06.8 says the line that matters is the one under the pointer or caret. Subtract the rest of the region: for each pointer stop or caret position, write one native-resolution crop of only the 3-5 lines around it (`hand_NN.jpg`, labelled with the stop's time), deduplicated with the block grid so a stop over unchanged code costs nothing. This adds what neither parent had alone: an image budget bounded by the number of stops, not by how much of the screen changed, so a fast-cut code screencast yields a handful of crops of the code being discussed instead of a crop per changed region. It also gives Linux, which has no OCR, a reading of the focused line, because the agent reads the crop itself. Judge: on the code screencast, count the questions answered from hand crops alone and the image tokens they cost against m03.4's full glyph sheet.

### m06.r1.2 Whose stillness is it: the app, the recorder, or the sensor
Builds on: m06.2 + m03.2
A dead click or a freeze (m06.2) is only evidence if the stillness came from the app. Screen recorders write variable-frame-rate files and drop or repeat frames under load, so "nothing changed for 3.8 s" can mean the app froze, the recorder stalled, or the pointer left the captured window. Read the stream's frame timestamps (ffprobe already runs) and the pointer track, and write the cause on the line: `no response 3.8 s after click (frames kept arriving: app)` against `(recorder wrote no frames 00:12-00:16: unknown)`. This adds a new entry to m03.2's blind-spot ledger: gaps in the recording itself, which a bug-repro report must not blame on the app. Judge: record the same scripted freeze with and without a CPU load that makes the recorder drop frames, and check the line names the right cause both times.

### m06.r1.3 The scripted session: a screen-recording bench whose answer key is the input log
Builds on: m07.1 + m07.6 + m06.6
m07.1 finds a free, timed key made by humans (SDH cues) for sound; m07.6 says a key must be at least as fine as the question. For screen recordings there is a key that is exact to the millisecond and free: drive a real app with a script (pointer moves, pauses, clicks, typos and their fixes, an injected 4 s server delay, three fast clicks on a disabled button) while the OS records the screen, and keep the script's own event log as the answer. Pushed further than either parent: the generator can mint as many recordings as a sense needs, in English and Vietnamese UI text, with every UX-research marker (hesitation, dead click, rage click, back-and-forth, correction) placed on purpose, so each of m06.1-m06.7 gets a judge before it is built and no human labels anything. Runs: an offline script and a few MB of generated media, regenerated like `bench/` media today.

### m06.r1.4 Screens named by their persistent text, and what changed between visits
Builds on: m07.2 + m06.4
m07.2 finds that text present from the first frame is never read; m06.4 wants a letter per distinct screen. Join them: OCR the full frame once per screen state, and use the set of persistent strings (a Jaccard match, not the pixel layout) to decide whether two moments are the same screen, so a Settings page that scrolled or had a toggle flipped is still screen A. Then subtract the strings that every visit shares (the chrome) and write only what differs between visits: `A Settings (0:03, 0:41): on 0:41 "Dark mode" is On, "Email" shows new@x.com`. That adds the researcher's most-asked question about a return visit, "what is different now", which neither a navigation letter nor a persistent-text line answers alone. Judge: scripted sessions from m06.r1.3 that change a setting and come back, with "what changed on the second visit" questions.

### m06.r1.5 The pointer trail drawn on the `look` sheet, not written on the card
Builds on: m03.7 + m06.1
m03.7 puts new senses into `look` first; m06.1 tracks the pointer the card throws away. Push it further by subtracting the text: `look VIDEO A-B --with pointer` draws the 15 fps pointer path onto the span's frames as a thin trail, with numbered dots at each stop and a ring at each click, so the agent's own eyes read the path, the pause and the target in one image, at no card tokens at all. The trial lane then measures itself: if the zoom log (m03.3) shows agents asking for the pointer on most screen recordings, the stop list (m06.1) earns promotion into `see`; if not, the card never paid for it. Judge: the scripted sessions' "what did they hover before clicking X" questions, answered from one trail image against the plain `look` sheet.

### m06.r1.6 One deixis gate for every kind of pointing
Builds on: m03.1 + m06.7 + m07.6
m03.1 gates camera motion behind a deictic word; m06.7 does the same with the pointer on screencasts. Generalise the gate to whatever is pointing in that 0.4 s: a pointer stop, a text selection (a block that turns selection colour), a drawn-in overlay that `see` already detects (an arrow, a circle, a highlight box), or a zoom-in, and print only the first one found: `say "đây là lỗi" (pointing: selection over line 42, 00:31.2)`. This adds one suffix rule in place of two senses, and it carries m07.6's resolution rule into the card: the suffix shows the gap between word and pointer to 0.1 s, so the agent and the bench both know how tight the match was. Judge: re-key phone reel q06 at 15 fps first (m07.6), then add deixis questions on screencasts from m06.r1.3, where the true pointing time is in the input log.
