## C07 Text for the agent's own eyes, and the text that never changes

## The concept

Two blind spots in one sense: **text**. Both are in the card today, and both have a cause in the code.

1. **Text that never changes is never read.** `_ocr_events` reads only the before and after crops of *changed* regions (`src/mediasift/see.py:290`). A headline banner that stays for a whole TikTok, a lower-third, or a slide title has no change event, so OCR never looks at it. In a fact-check, that banner is often the claim itself.
2. **Dense text that the card reads badly, the agent could read itself.** On a code screencast, the agent does not need a model's reading of the code. It needs the 3-5 lines in focus, at native resolution. The editor's own caret tells us where those lines are, and the picture pass already detects it as a blink. The card then points to small crops (`text_NN.jpg`), one per caret stop. The image cost scales with the number of stops, not with how much of the screen changed. Linux has no OCR, and the crops need none.

The surprising core has two parts. **First, the "new sense" is mostly a new use of evidence mediasift already computes and throws away.** The caret blink is in `sensed.json` today, filtered out as "pointer-sized jitter". The shot letters already say which frames show the same place. **Second, the reader is a better text reader than the sensor**, so for dense text the sensor's job is to aim, not to read.

**Who it is for.** The owner's own jobs:
- The TikTok fact-check and the Vietnamese reels, where the claim is a banner.
- Credited scripts from reels, which need the on-screen title and handle.
- The bug-repro screen recording, and any code or terminal screencast that the agent must quote exactly.

## How it works

### Part A: lasting text, read once per place

1. **Choose the frames to read. No new decode is needed.**
   - Take the flow frames already extracted under `frames/` (768 px wide, about 1 per second).
   - Take the first frame of each shot letter's first appearance (from `events.shot_letters`).
   - Add evenly spaced flow frames, so that no gap between read frames is longer than 10 s.
   - Cap the set at 30 Vision calls. For a one-shot reel, that is about 8 calls. For Tears of Steel, it is 30 (45 letters, capped).
2. **OCR each frame once** with the existing `ocr.read` (`en-US`, `vi-VT`, accurate level).
3. **Join the readings across frames.** Fold each string as `strip_watermarks` already does (letters only, lower case). Keep the most common reading of each string. Vision read `TRẮNG` in 75 frames and `TRĂNG` in 33, so the majority vote fixes diacritic noise. This is the cross-frame correction from psc2code (see prior art), without its language model.
4. **Decide what lasts.** A string lasts when two read frames at least 5 s apart contain it, in the same box (IoU ≥ 0.5).
5. **Find the exact span for free.** The string's span starts at the last cut, or the last event whose region covers its box, before the first frame that holds it. It ends at the first such event after the last frame that holds it. The 15 fps event list already holds those times. So the span is exact to 1/15 s, even though only ~1 frame in 10 is read.
6. **Exclude what is not new.**
   - Watermarks. Watermarks found here also go into the header, which fixes the `TikTok` miss above.
   - Strings that match speech: the same word test `_drop_captions` uses. The caption band stays with roadmap step 5.
   - Strings the card already prints.
7. **Print each string once.**
   - A string that spans at least half the video goes into the header, above the timeline. That keeps it when an agent pipes the card through `| head`.
   - Other strings go on one timeline line at their start.
   - The cap is 3 strings per line and 5 lines per card.

```
On screen throughout (read once): 00:00.5-01:13.4 "\"Treo biển\" Tử Vi"; "\"Bán thịt\" Bát Tự" (top)
...
01:34.9-01:48.1 pic text stays on screen: "def have_fun():"; "print(i)" (top-left)
```

A side effect is an [INFERENCE] to check on the bench. Changed-region fragments that are substrings of a lasting string (`"i Tre"`) can then be dropped from the timeline, which saves tokens.

On Linux, with no OCR, Part A does not run. The header says so in the existing `Not sensed:` line ("lasting on-screen text: no OCR on this OS"). It never stays silent about it.

### Part B: caret crops for the agent's own eyes (screen recordings only)

1. **Find the caret from events already computed.** On `python_100s`, the caret appears in `sensed.json` as a chain of `change` events:
   - Each event covers 1-2 grid cells, and each one undoes the event before it (`undoes` is set).
   - The events are spaced 0.47-0.53 s apart. That is one event per blink phase, which matches the Windows default caret time of 530 ms per phase.
   - The rule: **3 or more such events in the same ≤ 2-cell spot, 0.2-1.25 s apart**. The bounds are the per-phase limits of Microsoft's user setting, 0.4-2.5 Hz.
   - Measured on `python_100s`: 6 caret stops (96.5, 98.6, 104.5, 111.8, 119.1, 126.7 s). I checked one spot against the native frame. At 100.7 s, a single event covered x 280-320, y 280-360 (in 1280x720 pixels). The caret in that frame is at x≈305, y≈323, in `print(i)` (`develop/c07_py100.png`). A half-width crop of those lines reads cleanly at native resolution (`develop/c07_caretcrop.png`).
2. **Gate out false carets.**
   - Run on `screen` content only. Camera footage gave 1 false chain per video (3 of 3 tested), and this gate removes them.
   - Do not run when the analysed rate is below 5 fps. Files over 40 min are read at 2 fps, which is too slow to see a 0.5 s phase.
   - Require text beside the spot. On a Mac, Vision must read a line in the crop. On Linux, a cheap test: the rows beside the spot must show text-like horizontal edge density (no model).
   - The bilibili recording gave 3 chains, which this gate must sort out. The bench measures that.
3. **Crop.**
   - Take one crop per stop, at native resolution: the caret's line plus 2 lines above and 2 below. Line height comes from the 2-cell caret height.
   - The crop is half the frame wide and anchored on the caret: about 640 x 270 px on a 720p screencast.
   - Skip a crop when the grid blocks inside it have not changed since the last crop of that area. This gives one crop per distinct text state.
   - Pack up to 6 crops in two columns into `text_NN.jpg`, each labelled with its time.
4. **Write one card line, aimed at the image:**

```
01:36.5-02:07.5 pic caret stops (text in focus) at 96.5, 98.6, 104.5, 111.8, 119.1, 126.7 s -> text_01.jpg
```

   On a Mac, a bench arm may add the caret's own line as OCR text (`at 104.5 caret on "def have_fun():"`). That line ships only if the arm gains a question over the crops alone.

5. **Pointer stops are phase 2, behind a kill test.** m07.r1.5 noted that macOS and many recorders hide or redraw the pointer. A pointer tracker would also need a model, such as the 1.3 MB temporal detector below. So first count the frames with a visible pointer in the bench screencasts and the owner's bug-repro recording. If fewer than half show one, the pointer half stays parked.

Known ways Part B fails, each something the bench must contain:
- A caret set to not blink (VS Code `"cursorBlinking": "solid"`, or a terminal block cursor).
- A caret that stays solid while the user types [INFERENCE: common editor behaviour]. It was seen on `python_100s`: the caret moved at 100.7-102.1 s with only 1-2 events, so no chain formed.
- Recordings below 5 fps.
- Blinking UI badges or record dots, which the screen-only and text-beside gates must stop.

## Prior art (with URLs)

- **psc2code** (Bao et al., ACM TOSEM 2020) extracts code from programming screencasts.
  - It drops near-identical frames (NRMSE < 0.05) and uses a CNN to remove non-code frames.
  - It crops the code-editor sub-window, OCRs it with Google Vision API, and corrects errors with cross-frame voting and a code language model.
  - It treats the cursor as **noise**: the cursor over an "s" made Vision read "f", and the caret is often read as "i" or "I".
  - C07 turns that noise into the anchor. It gives pixels to a vision reader instead of OCR text. It uses no CNN and no cloud. Part A takes psc2code's cross-frame voting.
  - https://soarsmu.github.io/papers/2020/Bao2020psc2code.pdf, https://dl.acm.org/doi/abs/10.1145/3392093
- **CodeTube** (Ponzanelli et al.) is described in psc2code. It OCRs every frame and filters out bad identifiers as noise. Also related: an MSR 2020 study of OCR accuracy on screencast code: https://doi.org/10.1145/3379597.3387468
- **cursor-motion-detector** (ldenoue) is closest to the pointer half.
  - A temporal MobileNetV4 (1.29 M parameters, about 1.3 MB ONNX) reads grey plus two frame-difference channels. It predicts the arrow tip or the **text insertion point**.
  - On synthetic data: 98.8% precision within 8 px. The author says a real-recording benchmark "remains essential".
  - C07 Part B gets the caret from blink chains that mediasift already computes, with no model. This detector is the candidate for phase 2 (pointer stops), pinned by SHA, only if the visible-pointer count passes. https://github.com/ldenoue/cursor-motion-detector
- **Video OCR of superimposed captions** (Sato, Kanade et al., 1999) used temporal redundancy across frames to read overlay text in news video. Commercial "lower third detection" products do the same. Part A's reading method is old. What is new is the delivery: read once per place, with exact spans from events already computed, inside a per-token budget. https://doi.org/10.1007/s005300050140, https://staging.digital-nirvana.com/blog/video-ocr-on-screen-text-search/
- **Gemini video understanding** samples 1 fps and warns that "fast action sequences might lose detail". The industry default has the same ~1 fps limit as the flow sheets, which is why aimed crops matter. https://ai.google.dev/gemini-api/docs/video-understanding.md.txt
- **Claude image cost.** An image costs ⌈w/28⌉ × ⌈h/28⌉ visual tokens. The standard tier caps the long edge at 1568 px and 1568 tokens. Claude 4.7 and later cap at 2576 px and 4784 tokens. https://platform.claude.com/docs/en/build-with-claude/vision
- **Caret blink time.** The Windows default is 530 ms per phase, and users can set 0.4-2.5 Hz. https://superuser.com/questions/815367/how-to-set-cursor-blink-rate-1-or-1-2-second, https://learn.microsoft.com/en-us/previous-versions/windows/desktop/dnacc/flashing-user-interface-and-the-getcaretblinktime-function

Nothing I found does Part B's exact move: find the caret from a block-grid blink chain, then hand native crops to an LLM reader. The pieces exist separately.

## What it costs to run

| cost | Part A (lasting text) | Part B (caret crops) |
|---|---|---|
| CPU/GPU per run | at most 30 extra Vision calls on frames already decoded. Measured 0.05-0.16 s per 768 px frame on the M1 Pro under `nice 10` (15.6 s for 99 frames, 14.5 s for 274 frames of film). Typical cost is 1-3 s; the worst case is about 5 s, on top of today's 4-24 s of OCR | the chain search is a pass over events already in memory (milliseconds). Crops need one ffmpeg seek pass at native width for 6-20 times (about 1 s). No model |
| memory | Vision in the existing process, inside the existing autorelease handling. No new peak, and nothing next to MLX's 3.3 GB | none extra |
| Linux / GPU box | does not run. One `Not sensed:` phrase says so | runs fully. It needs no OCR (the text-beside gate uses an edge test) |
| card tokens per read | 0 on film (measured 0 lasting strings on Tears of Steel, Big Buck Bunny and `reel_en`). About 20-40 tokens per string, at most 5 lines | one line, about 30-40 tokens, on screen recordings with caret stops only |
| image tokens, only when opened | none | one 640x270 crop is 23 × 10 = 230 visual tokens. A sheet of 6 crops (1280 x 810) is about 1,334 tokens. For comparison, one full 1280x720 frame (`look -n 1`) is 1,196 tokens, and a 4 x 3 flow sheet (1280 x 540) is 920 tokens, but its code is unreadable at 320 px |
| disk | none (text in `sensed.json` and the card) | about 100-200 KB per `text_NN.jpg` |
| $ / quotas | $0. Local only, no API, no download, nothing to pin | $0 |
| things that break or need watching | Vision's Vietnamese diacritics (majority vote reduces this); animated or scrolling banners (they fail the same-box test and are left out, never half-printed); a change in `shot_letters` thresholds changes which frames are read | editors with a solid caret, and recorders under 5 fps (both fail quietly as "no crops", so the card adds one `Not sensed: caret (no blinking caret found)` phrase on screen recordings, never silence); UI blinkers (gated, and measured on the bench); new screencast styles need a bench item before they are trusted |

Runs: Part A runs inside `see` on macOS only, after the picture pass, with at most 30 Vision calls on cached flow frames; its output is header or timeline lines plus a `lasting_text` list in `sensed.json`. Part B runs inside `see` on screen recordings at 5 fps or more, on every OS, as a pass over the event list plus one ffmpeg seek pass for crops, and writes `text_NN.jpg`. Neither part adds a model, a download, a network call or a background process. Each part ships only after its bench arm passes the kill rules above.
