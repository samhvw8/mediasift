Reading I picked: the brief covers every input, but my lens only bites on **screen recordings and
screencasts** (the bug-repro recording and the fast-cut code screencast that drew 20 of the 61 zooms).
I read "what the agent cannot perceive" as including *what the person operating the screen did*, not only
what the pixels did.

Evidence from the code that shaped every idea below: `see.listed` drops small motion on purpose
(`src/mediasift/see.py` ~line 723: "pointer-sized jitter: visible in the flow frames, too noisy as
text"). So the cursor, the one object a UX researcher watches first, is deleted before the card is
written. And the flow sheets run at about 1 frame a second, which cannot show a pointer path or a pause
before a click. The card lists effects (a region changed) and leaves out the cause (a hand moved,
stopped, clicked, typed, waited).

Subtraction, run step by step (remove one part, see what is left):
1. Remove the screen and keep only the pointer: a path with stops. That is a hesitation map (m06.1).
2. Remove the change detector and keep what it ignores, stillness: waits, dead clicks (m06.2, m06.3).
3. Remove time and keep the distinct screens: a navigation graph, showing back-and-forth (m06.4).
4. Remove the region and keep the text that grows and shrinks inside it: typing and corrections (m06.5).
5. Remove the video and keep only the input: a repro script (m06.6).
6. Remove speech's need for a gesture detector: on a screen the pointer *is* the gesture (m06.7).
7. Remove OCR on changed regions and OCR around the pointer and caret instead (m06.8).

## Baseline (the obvious answers)
- Track the mouse cursor and add its position to `pic` lines.
- Detect clicks from the click sound (CED "Tick"/click) synced to a picture change.
- Run OCR more often or at higher resolution on code screencasts so small text survives.

## Assumptions I broke
- **Change is the signal**: for a UX researcher the strongest signal is what does *not* change. A pointer
  that stops for 2 s over a button and then moves away (hesitation), a click after which nothing changes
  for 4 s (dead click, latency), a screen that comes back for the third time (lost). A change detector
  is blind to all three by design, and the card filters out the only moving thing (the pointer) that
  would reveal them.
- **The video is the subject**: in a screen recording the subject is the person behind it. The pixels
  are a side effect of their input. Questions like "where did they get stuck", "what did they try
  before the error", "did the app react to that click" are about the input, and today the agent must
  rebuild it from 1 fps tiles, which explains the many 1.4 s zooms.

## Ideas
### m06.1 Pointer trail with stops (the ghost track)
Subtract everything except the pointer: find the small, fast-moving blob that `listed` currently throws
away, track it at the 15 fps the picture pass already reads, and write only its **stops** (still for
>= 0.6 s) and the OCR'd label under each stop: `ptr stopped 2.1 s over "Delete account", left without
clicking`. A researcher reads a session as a sequence of stops, not a stream of positions, so the line
count stays small (stops, not frames). Not obvious because the jitter filter exists for a good reason:
pointer motion as *change events* is noise, but pointer *stops* are rare and full of meaning. Judge:
hand-label stops and hover targets on 3-4 screen recordings; questions like "what did the user hover
before clicking Save".

### m06.2 Stillness after action: latency and dead clicks
Subtract the change detector's assumption that nothing-happened is nothing to report. When an input
lands (pointer stop + click sound, or a keyboard burst) and the screen stays still, or only a small
spinner-sized area keeps changing, write `pic no response for 3.8 s after click at 00:12.3 (only a
spinner kept changing)`; when nothing changes at all within 2 s, `dead click`. This is the bug-repro
question ("it froze when I clicked") that today needs several zooms to confirm, and it costs nothing:
the grid already knows every frame's distance. Judge: bug-repro recordings with known freezes; the
answer is the measured gap, checkable against frame numbers.

### m06.3 Rage clicks and repeated attempts
Count repeated input at one spot: 3+ clicks within ~1 s in the same pointer stop, or the same control
clicked again after a dead click. Product analytics (session replay tools) treat rage and dead clicks as
the two highest-value frustration markers, and mediasift already counts short sounds and blinks, so
"how many times" is a shape the card and agent already understand. Not obvious because it is a
*behaviour* label, not a sensor reading; the evidence (count, spot, times) stays on the line so the
agent can judge. Judge: count questions on recordings with staged repeated clicks.

### m06.4 Screen letters: a navigation map with returns
Subtract time and keep the places: give each distinct screen state a letter the way cuts get shot
letters (the shot-matching already exists), named by its biggest OCR'd heading: `SCREENS A Settings
(0:03, 0:41, 1:12), B Billing (0:20, 0:55)`. Going A-B-A-B is the researcher's "the user is lost"
signal, and for the agent it answers "how many times did they go back to Settings" and "what screen was
open when the error appeared" in one line instead of a sheet hunt. Not obvious because screens rarely
*cut*: navigation is a large region change, so the letters must key on page layout, not on cuts.
Judge: sequence and count questions on 2-3 navigation-heavy recordings.

### m06.5 Typing, with its corrections
Subtract the region and keep the text inside it: when OCR in one small region grows a few characters at
a time, merge it into one line, `typed "pasword" -> "password" in the field at top (0:14-0:19, one
correction, 3 s pause after "pas")`. A researcher learns most from corrections and pauses inside input
(what the user was unsure about); the agent today sees dozens of OCR fragments or none. It also helps
the code screencast: code being typed becomes one line with its final text, not 20 small changes.
Judge: recordings with known typed strings; questions "what did they type first", "what did they fix".

### m06.6 The repro script: a card with no video in it
Subtract the timeline of effects and write only the user's actions in order, numbered, as a second
small file (`steps.md`) for screen recordings: `1. 00:03 click "Settings" 2. 00:07 typed "..." in
Email 3. 00:12 click "Save" 4. waited 3.8 s 5. 00:16 dialog "Invalid token"`. This is the exact output
the bug-repro job wanted, built only from m06.1-m06.5 events, and it costs the agent fewer tokens than
the full card. Not obvious because it inverts the card: steps first, picture second. Judge: compare
against a hand-written repro for each bench recording (step recall, order, times within 0.5 s).

### m06.7 The pointer is the gesture: deixis for screencasts
The bench's one shared miss is timing a gesture to a spoken phrase. On a screencast the narrator's
gesture *is* the pointer (or a text selection). When a `say` line holds a deictic word ("this", "here",
"that button", "cái này", "ở đây"), attach the pointer stop or selection under it: `say "click this
one" -> ptr over "Deploy" (00:42.1)`. Only deictic lines get it, so the token cost is a few words on a
few lines. Judge: add deixis questions on screencasts to the bench, which today only asks them on camera
footage.

### m06.8 Read where the hand is, not where the pixels changed
Subtract "OCR the changed region" and OCR a small window around the pointer stop and the text caret
instead. On a fast-cut code screencast most of the screen changes at once, so changed-region OCR reads
everything or nothing; the caret and pointer mark the 2-3 lines the narrator is talking about. That is
probably why 20 zooms landed on one code video: the agent was hunting for the line in focus. Judge:
replay those 20 recorded zooms as questions and count how many the caret/pointer window answers without
a `look`.

## The provocation I would put to the group
On a screen recording the card describes what the screen did, but every question people ask is about
what the hand did and where it stopped, and the one sensor that could answer that, the pointer, is the
part mediasift deletes as noise.
