## Builds

### m06.r2.1 The agent as its own screen recorder: the UX lens's kill condition, removed
Builds on: m04 provocation + m06.r1.3 + m04.r1.6
The one thing that, if true, kills every pointer, click and hesitation sense: the owner almost never hands the agent a screen recording (one bug-repro in a month of logs), so these senses would never meet a real question. m04 found the owner's media is mostly media the agent made itself; subtract the human recorder and let the agent record its own UI work (`screencapture -v -k` with clicks shown, or a Playwright run) and sense the recording before it says done, with the driving script's event log as the free answer key (m06.r1.3). Screen recordings then become the commonest input instead of the rarest, and each "owner caught it after done" item from m04.r1.6 (a dead button, a slide-like transition) turns into a scripted rerun that the card must catch first. Judge: count, over two weeks, how many agent-made UI changes get a recording and how many owner complaints the card had already flagged.

### m06.r2.2 Frozen app or frozen recorder: the pointer is the witness
Builds on: m04.3 + m06.r1.2 + m02.r1.1
m04.3 flags a frozen picture while audio continues, and m06.r1.2 asks whose stillness it is by reading frame timestamps. Kills it: many recorders (and every re-encode, and the owner's joined crash pieces) write constant-frame-rate files that repeat the last frame, so timestamp gaps vanish and the frame-arrival test says nothing. The version without that flaw uses a second witness in the m02.r1.1 style: the OS composites the pointer on its own path, so pointer still moving over frozen pixels means the app froze, and pointer frozen with the pixels means the recorder or the join froze. One health line carries both: `picture frozen 41:12-41:50 (pointer moving: app hung)` against `(pointer frozen too: recording stalled, not the app)`, which is the difference between filing a bug and re-recording.

### m06.r2.3 Responsiveness numbers per click: time to first response and time to settle
Builds on: m04.1 + m06.2 + m06.8
m04.1 reads how motion feels from the 15 fps grid series; m06.2 finds clicks that get no response. Subtract the description of what changed and keep only the two numbers a UX researcher writes beside every action: time from click to the first changed block near the pointer, and time until the screen stops changing (`click "Save" 00:12.3: first response 0.9 s, settled 3.4 s, spinner between`). This adds a per-action latency ledger that neither parent had, and it is exactly what the agent needs to say "the fix made it faster" with a number, as the repo's own rules demand. Kills it: macOS recordings do not draw clicks by default; without the click ring the click time is a guess, so the version that survives takes the click time from the driving script (m06.r2.1) or from `-k`, and prints nothing on footage where neither exists. Judge: scripted clicks with injected delays of 0.2, 1 and 4 s.

### m06.r2.4 One deixis gate for eye and ear, and a check that kills it cheaply
Builds on: m06.r1.6 + m05.r1.5 + m02.r1.1
m06.r1.6 gates pointing words ("this", "here", "đây") to a pointer, selection or overlay; m05.r1.5 gates listening words ("hear that", "nghe này") to the next 3 s of tagger scores. Join them as one rule: the word class picks the sense, so `say "đây là lỗi"` gets a pointing suffix and `say "nghe này"` gets a sound suffix, and a phrase that has both ("look at this, hear that click") gets both with the gap between them, which is the bench's one shared miss (timing a gesture to a phrase). Kills it: deictic phrases may be too rare in real speech to earn a rule. That is checkable for free before anything is built: count gated phrases across the cached transcripts in English and Vietnamese, and build only if they appear in more than a set share of videos.

### m06.r2.5 `diff` for two runs of the same flow: did the fix change what the user sees
Builds on: m02.r1.3 + m06.r1.4 + m06.r2.3
m02.r1.3 aligns a clip with its source by frame hashes and word times; screen recordings of the same flow before and after a fix share almost no pixel hashes (different data, window size, theme), so push the diff onto the persistent-text screen names from m06.r1.4 instead. Align the two runs screen by screen and print only what differs: `screen C Checkout: error banner "Payment failed" gone; click "Pay" settled 3.4 s -> 0.6 s; screen D new`. This turns the bug-repro job into a regression check the agent runs on its own fix, with no description of either video at all, and the answer key is the pair of driving scripts. Judge: scripted flows run twice with known changes (a removed banner, a changed delay, an added step).

### m06.r2.6 Fresh: the hesitation ledger as the honest "I could not tell" for screen recordings
Builds on: m05.r1.4 + m06.1 + m06.r1.5
m05.r1.4 measures where the mix hid the words and says so instead of guessing. A screen recording has its own blind spot: the pointer stops for 2 s over a menu, and the card cannot know whether the user was reading, confused or away. Subtract the interpretation and print only the measured stop with what was under it (`stop 2.1 s over "Export" menu, no click, then back`), and route the "why" to the agent's own eyes through the `look` trail (m06.r1.5) or to the user. Kills it: if stops are as common in calm use as in confusion, the line is noise; the scripted sessions with planted hesitations against plain runs measure that before any line reaches the card.
