## C10 A cache that knows its age and a card that says how much was sensed

## The concept

**For whom.** The agent that reads a card, and the owner who reads that agent's answer. The failure
it prevents is a quiet one: the agent says "the video claims X" when mediasift heard nothing, or it
runs a zoom command that no longer exists and then guesses.

**What it is.** Two honesty rules, enforced in code:

1. **A card never claims more than was sensed.** When a web fetch or a backend fails, `see URL` does
   not stop with an exception and leave the agent with only the post text. It steps down a ladder
   (full sense, then storyboard plus platform captions, then the info JSON only). The card's first
   line names the rung it reached, what is therefore missing, and the priced command that would
   climb back up.
2. **A card never outlives the binary that prints it.** The header (commands, sheet list, "how to
   use") is rendered from the current binary every time the card is read, including on a cache hit.
   `sensed.json` records which sensor revision made each track. One test walks the real cache and
   fails on any card that prints a dead command or holds a stale track without saying so.

**What makes it surprising.** Every other shortlisted idea adds a sense. This one adds none. It
says the most dangerous card is not a wrong line but a *partial* card that looks complete, and the
evidence for that is already on disk (below). It also flips the cache from "a format bump throws
everything away" to "a format bump re-renders, and a model bump re-senses one track".

## How it works

Four parts, in the order they pay off.

### 1. The sensing ladder for `see URL` (the core)

```
rung 3  full        video + audio downloaded; every sensor ran           (today's only success path)
rung 2  peek        storyboard sprite + platform captions + info JSON    (no audio heard)
rung 1  post only   info JSON: title, uploader, date, description        (nothing in the video sensed)
rung 0  nothing     fetch failed outright                                (exit non-zero, as today)
```

- `fetch()` stops raising on "no merged video". It returns what it got, and `see` picks the highest
  rung those files support.
- Rung 2 on YouTube: `yt-dlp -j` already lists storyboard formats. For Tears of Steel today they are
  `sb0` 432x180 tiles in 3x3 grids over 17 fragments (153 frames over 12:14, about one every 4.8 s),
  down to `sb3` 48x27. The frames go through the picture pass at that rate. OCR runs on the tiles, the
  shot letters come from the 32x18 grid, and the captions become the `say` lines (the code already
  does "site subtitles replace ASR").
- Platforms without storyboards (TikTok, Facebook) have no rung 2. They fall to rung 1, and the card
  says so plainly. The ladder is honest about platforms as well as failures.
- **The first line of the card is the rung**, built from the existing `Sensed:` / `Not sensed:`
  lines (`s.holes` already exists, so this extends it rather than adding a new card section):

```
SENSED: storyboard + auto-captions only (rung 2 of 3). Audio NOT heard: no sounds, no voices,
speech is YouTube's auto-captions, picture is 1 frame per ~5 s at 432x180.
Do not describe sounds or tone. To sense fully: `yt-dlp -U` or install deno (yt-dlp warned: no JS
runtime), then `mediasift see URL --force` (~1-2 min for this length).
```

```
SENSED: post text only (rung 1 of 3). Nothing in the video was seen or heard.
The claims below are the uploader's description, not the video's. Fix: `--cookies-from-browser chrome` (facebook asked for login).
```

- The fix hint is chosen from the yt-dlp stderr by a small table: login required gives the cookies
  hint, the JS-runtime warning gives deno, rate limiting gives "wait, or `--on HOST`", and an unknown
  error gives `yt-dlp -U`. Each hint carries its price in minutes, from the same `duration` the info
  JSON already holds and the measured seconds per minute of video in `usage.jsonl`.
- A lower-rung card is cached under its own variant (`rung=2`), so a later `--force` that reaches
  rung 3 replaces it and nothing old is served as full.

### 2. Read-time header

- `card.md` stores only the timeline body. `see` prints the header from `sensed.json` and the current
  binary each time: tool name from `sys.argv[0]`, the zoom command, the sheet list (from the files in
  the dir), and the rung line.
- Taken from m08.1: the "How to use this card" block (~950 chars, ~240 tokens, 43% of a median card)
  shrinks to one line that points at the skill, which already says the same thing. That is a token
  cut on every card, and it must hold the bench score (see the test below).
- **Split the cache key.** `CARD_VERSION` leaves the key. The key becomes content plus sensing
  settings (`--asr`), and the format version is checked at read time instead. A format bump then
  re-renders from `sensed.json` in milliseconds and stops orphaning the whole cache. This needs
  `flows` and `refs` (event-to-sheet rows) saved in `sensed.json`, which today they are not.

### 3. Per-track sensor revisions (the "knows its age" part)

- `sensed.json` gains `tracks: {picture: "grid-v3", sound: "ced-small@06bb40c5+mood-v1",
  speech: "quan@13c3a2c"|"parakeet-mlx@<rev>"|"subs:youtube-auto", ocr: "vision-macos", rung: 3}`.
  Each module owns one constant next to its pin (`QUAN_REV`, `CED_REV` already exist), so a bump in
  code is a bump in exactly one place.
- On a cache hit, a track whose revision differs from the current constant is **stale**. The header
  prints one line, `speech: quan@13c3a2c, current quan@9f1e; --refresh speech re-runs it (~30 s)`,
  and `see --refresh speech|sound|picture|ocr` re-senses that track only and patches `sensed.json`.
  Re-sensing by default is rejected, because a pin bump would then silently cost minutes on every
  long file the first time it is read. The agent or owner decides. This is taken from m08.r1.1, and
  it beats folding pins into the key (m02.8, m02.r1.6).
- **Known defects** (m05.r1.1). A small table in code maps a track revision to a defect it is known
  to have (`quan@13c3a2c: no ASR loop guard`). When the table matches, the header prints it once.
  Healing only the flagged span (m04.r2.4) is a later step, built only after the loop guard and
  speech-health check exist and are benched. Until then the honest line is enough.

### 4. The invariant test over the real cache

- `tests/test_cache_invariants.py` has two modes. In CI it checks a fixture of 3 cards (old version,
  stale track, rung 2). Locally, with `MEDIASIFT_CHECK_CACHE=1`, it walks `~/.cache/mediasift/see/*`.
- It asserts four things. Every command a printed card names resolves on PATH and its subcommand
  parses with `cli.main(["--help"])`-style dry parsing. Every stale track is announced in the header.
  Every card below rung 3 has a rung line. No unreachable dir is older than N days (this feeds a
  `mediasift cache prune`, which reclaims the 2.49 GB).
- Today it fails on 733 cards, so it is the failing test the house rules ask for.

## Prior art (with URLs)

- **Build systems already do part 3.** Snakemake re-runs a job when its code, params, inputs or
  software environment change (`--rerun-triggers {code,input,mtime,params,software-env}`), so a stale
  output is detected per rule, not per workflow:
  https://snakemake.readthedocs.io/en/stable/executing/cli.html . DVC records each stage's
  dependency hashes in `dvc.lock`, and `dvc repro` re-runs only stages whose dependencies changed:
  https://dvc.org/doc/command-reference/repro . **What is different here:** those tools re-run
  automatically. mediasift should *announce* staleness and price the re-run, because the consumer is
  an agent paying per turn and a long file costs minutes, and silently serving the old track is the
  default it has to break, not automatic recomputation.
- **Storyboards exist and are reachable, but not as images.** `yt-dlp -F` lists YouTube storyboards
  as `sb0`-`sb3` `mhtml` "images" formats (verified locally today with yt-dlp 2026.08.19 on
  `https://www.youtube.com/watch?v=R6MlUcmOul8`). Turning them into jpgs is an open feature request,
  https://github.com/yt-dlp/yt-dlp/issues/2048 , and converting them to video is another,
  https://github.com/yt-dlp/yt-dlp/issues/11386 . Bilibili storyboard support is a pending patch:
  https://github.com/yt-dlp/yt-dlp/issues/10441 . So rung 2 needs a small mhtml unpacker of our own,
  works for YouTube now, may work for Bilibili later, and does not exist for TikTok or Facebook.
- **Silent degradation in the fetcher is real and current.** yt-dlp now warns that YouTube extraction
  without a JS runtime is deprecated and that "some formats may be missing":
  https://github.com/yt-dlp/yt-dlp/wiki/EJS . This is the kind of quiet partial failure the rung line
  is for. Open issues like https://github.com/yt-dlp/yt-dlp/issues/17812 (formats skipped as DRM,
  high priority, 2026-10-16) show the extractors keep changing under us.
- **Nothing found that does the whole thing.** I found no video-to-text tool for agents that states
  which rung of sensing a summary rests on. The common pattern in the transcript tools is "fall back
  to captions" with no flag on the output, which is the exact failure this concept prevents. This is
  stated with medium confidence: the search was short, and the tools in that space change quickly.

## What it costs to run

- **CPU/GPU:** none at sense time. Rendering the header is milliseconds. Rung 2 *saves* compute (a
  storyboard is a few hundred KB instead of a video download plus decoding). `--refresh` runs only
  when someone asks.
- **Tokens:** net negative. The header drops from ~240 tokens to about 1 line on every card. The rung
  line adds about 40-60 tokens, and only on degraded cards (5 of 7 real URL attempts so far).
  Staleness and defect lines appear only when they apply.
- **Disk:** negative. `cache prune` reclaims the 2.49 GB of unreachable cards now, and the split key
  stops each format bump from orphaning the cache again.
- **Maintenance:** three things must keep up, and the design keeps each in one place.
  1. The stderr-to-hint table follows yt-dlp's error wording. When the wording drifts, the hint falls
     back to `yt-dlp -U` and the rung line is still correct, so drift can make the advice generic but
     can never make the card dishonest.
  2. Each track revision constant sits next to its model pin.
  3. The known-defects table gains a row only when a fix ships.
  The cache-walk test is what stops all three from going stale quietly.
- **Breaks or needs watching:** the mhtml storyboard unpacker depends on YouTube's sprite layout, and
  that is the one fragile piece. If it breaks, the ladder falls to rung 1 with a correct line, so the
  break shows up as worse coverage, not wrong claims.
- **Not built:** auto-healing flagged spans (m04.r2.4) and re-sensing by default on a pin bump. Both
  spend compute without being asked, and the measured saving (1-4 min per long file) does not pay for
  that risk yet.

**Runs:** nothing new. No service, schedule, model or download is added. The changes are a read-time
header, a fetch fallback that keeps files yt-dlp already wrote, one revision field per track, a
`cache prune` subcommand and one test.
