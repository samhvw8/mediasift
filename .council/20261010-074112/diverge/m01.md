## Baseline (the obvious answers)
- Keep cherry-picking, but add OCR on screen frames, a semantic keyframe veto, and an audio-event tagger (laughter, music, alarm) whose output is text lines in the storyboard.
- Wrap the existing pipeline in an MCP server or a single zero-flag `framesift VIDEO` command, with the card/find/read/look verbs from the 261002 brainstorm.
- Add a local VLM captioner that writes a per-segment "what changed" paragraph, so the agent reads text instead of image grids.

## Assumptions I broke
- The sensor's job is to turn the video into something the agent reads up front: the contrarian lens says the up-front pass is the cost. The 8-minute podcast analyse is paid for every video, but the agent asks about it once, or never. Pay at question time, or at record time, not at ingest.
- Pixels are the right raw material: for the user's most frequent video (screen recordings of bugs and UI flows) the pixels are a lossy re-encoding of an event stream (clicks, DOM, console, network) that existed one step earlier. Everyone is working harder to decode a signal that was thrown away upstream.
- Local-first means the whole sensing stack must be local: the user's own weights say operational burden and infra cost dominate. A stack that is "hard to run daily" is already failing the operational test. A metered API call that costs cents and has no moving parts may beat 2.4k lines of Python and three ASR backends.
- "Temporal understanding" needs more frames: it may need fewer, composited differently (one image that contains motion), or no frames (a text diff).

## Ideas
### m01.1 Stop sensing the video; sense the recording
For screen recordings, add a recorder (`framesift rec`, or a hook for the repro tools the agent itself runs) that writes a sidecar timeline while recording: cursor, clicks, keystroke events, focused window, console errors, network calls, DOM mutations. The video becomes a thumbnail; the agent reads the event log (which is exact, cheap, greppable and has cause then effect built in) and looks at a frame only at an event timestamp. For the third-party videos that remain, nothing changes. Not obvious because it turns the product from "video sensor" into "recording format", and removes the hardest ML from the most common use.

### m01.2 One image that contains motion: the chronophoto
Instead of N keyframes laid side by side, composite one frame per segment as a motion-history image: the final frame sharp, earlier positions ghosted at falling opacity, with optical-flow arrows and a small time ruler. A single 1-1.5k-token image then carries direction, speed and order, which a tile grid cannot. Targets the exact gap (what moved where, what happened between A and B) at flat image cost. Cheap to test with synthetic clips (m01.8). Everyone tries to add frames; this adds a dimension to one.

### m01.3 Make sound visible: a labeled spectrogram strip on the same time axis
Render audio as a thin image under the frame strip: log-mel spectrogram, pitch contour, loudness curve, silence gaps shaded, words printed on top where ASR placed them, and tick marks shared with the frames. A vision model reads a spectrogram well enough to see "music starts", "voice rises", "long silence" and "clap", and it is aligned with the picture by construction. It needs no audio-LM and no tagger vocabulary, only the signals framesift already computes (the log-mel novelty). The tagger is the crowded answer; the picture of the sound is the unused one.

### m01.4 No ingest at all: `look` is the whole product
Delete analyze, index, segments and the storyboard from the default path. Ship a stateless `fs VIDEO --at 12:30 --span 20 [--grid 4x3] [--audio]` that is just ffmpeg plus a labeled sheet plus a whisper pass on the span only, with a content-hash cache so repeat asks are free. The agent binary-searches the video itself, as a person scrubs; it already greps and reads cheaply, and a 1 h video costs nothing until someone asks. The bench found that agents grep the storyboard anyway, and the long-video arms were all 8/8. Cost after shipping: near zero, nothing to babysit; the cost moves into the agent's own turns, which I admit I cannot price (risk: more round trips).

### m01.5 Hook, not command: the user never types a thing
The daily-use problem is invocation, not stack. A `UserPromptSubmit` hook (or a path-watcher on a `~/Movies/agent-inbox` folder) spots a video path or YouTube URL in the prompt, runs the fastest tier in the background, and injects a 300-token card: duration, language, a handful of hooks for what to ask next, and the exact `fs look` line. Deeper tiers run only when the agent asks. No daemon: the hook is a short-lived process. Not obvious because it treats "one command" as still too many.

### m01.6 Rent the ears and eyes: the native-video API as the sensor, local as the fallback
Gemini-class models take video and audio natively, and hear music, laughter and tone, which no local stack here will. Make the sensor a one-shot call that takes the video plus the agent's question and returns text with timestamps, with the result cached. Running cost per hour of video looks like cents to tens of cents (unverified: check current per-second token rates before believing it), against zero ops, zero models to update, zero GPU box to wake. This argues against the local-first default for the one place it hurts most (non-speech audio). Keep a flag to decide per video, with the cost printed; the risk is quiet data egress, so make it opt-in per file.

### m01.7 Captions are the wrong currency; text diffs between frames are the right one
Do not describe frames, describe changes: a small local VLM gets frame N and N+1 (or a sampled pair around each segment boundary) and writes one line, "the modal closes, the row turns red, the counter goes from 3 to 2". Store the chain as a change log, like git log for a video. Cause then effect reads directly as text, is greppable, and costs no image tokens in the agent's session. It differs from the baseline captioner because the unit is the delta and the output is a causal log, not a scene description.

### m01.8 Prove it with videos whose truth we wrote
The bench never tested temporal or audio questions because there are no ground-truth videos. Generate them: a script renders synthetic clips (shapes moving, a UI that clicks through N steps, a tone that rises, a clap at t=7.3, counted repetitions) with the answers known by construction, plus a few real clips labelled by hand. Every claim in this brief (chronophoto beats tiles on motion, spectrogram beats nothing on non-speech audio) becomes a number in minutes, at zero cost, for each new idea. This is the cheapest part of the whole plan and should come first.

## The provocation I would put to the group
The agent does not need to see the video; it needs the answer to the next question, so build the cheapest thing that answers questions (or captures the events at record time) and stop pre-digesting every video it will probably never ask about.
