## Baseline (the obvious answers)
- One command `framesift VIDEO` that defaults everything (ASR on, index on, auto output dir).
- Wrap it as an MCP server / Claude Code skill so the agent calls it itself.
- Cache results by file hash so the second run is instant.

## Assumptions I broke
- "The sensor is a tool the agent calls": a daily tool is one nobody calls. Daily use means the harness meets the video already digested, so the sensor must run before the agent asks (a hook or a folder watch), not on request.
- "The output is a folder of files the user names": the output folder, the flags and the setup are the daily friction. The daily operator removes the output path entirely: the video's own location plus its hash is the address.
- "Run it on the whole video": a daily user asks about a 90-second repro or one timestamp far more often than about a 2 h podcast. Lazy, range-first work beats whole-file analysis, so the cost matches the question.

## Ideas
### m02.1 The sidecar: analysis lives next to the video, made by a hook, not by a command
A Claude Code UserPromptSubmit hook (or a Finder/launchd folder action on ~/Movies, ~/Downloads, the screen-recording folder) spots a video path in the prompt, or a new file in a folder, and starts a cheap detached `framesift` pass. It writes `clip.mp4.fs/` beside the file (like `.DS_Store`, keyed by size+mtime+head hash). The agent's first read of the path finds a ready 10 KB card. There is no always-on daemon: the hook is spawned by the prompt, runs once and exits. This is the only design where the user types nothing, and "waiting" happens while he is still typing the question.
### m02.2 Time-boxed tiers: the first answer is ready in under 5 s, and it gets richer on its own
Today the whole pipeline is all-or-nothing (63 s for 2:23, 8 min for 1h45). Make it a ladder that writes after each rung: T0 ffprobe + I-frame-only map (seconds, even for 2 h), T1 card with sparse keyframes, T2 ASR, T3 index. Every output file is stamped with its tier, and the card ends with "tier 2 of 3, ASR running, re-read in 40 s". The agent never blocks, and a failed rung leaves earlier rungs valid (crash beats corrupt, but partial is labelled, not hidden).
### m02.3 Zero-flag auto-profile: content type decides everything, and the choice is printed, not asked
`content: screen|camera` already exists. Extend it to a profile (screen repro, talk, podcast, film) picked from the first 20 s and from ffprobe (audio-only video, no motion, resolution, duration), setting ASR model, language (Whisper detects en vs vi), drift, and max segments. The card's first line says what was picked and the one flag that overrides it. Flags stay as an escape hatch the daily user never sees: the SKILL.md tuning table shrinks to a single sentence.
### m02.4 A doctor + install path with one honest failure: `framesift doctor` and a single-binary-feeling install
Daily use dies at the first broken dependency: llama-server version b11501, a Python 3.14 pin, the optional [asr] extra, ffmpeg. Make `mise run install` (or `uv tool install`) pull everything, and add `framesift doctor` that checks each piece, tells what to run, and exits non-zero. On first use with a missing dependency it fails loudly with that one line, never a degraded silent run. The cost to measure is "minutes from a clean Mac to first card", and I would put a number on it.
### m02.5 Pull the model server out of the per-call path: embed once at analyze time, query with a text-only embedder in-process
`find` starts and stops llama-server each call (about 2 s, plus a binary to version-pin). Daily operator view: that dependency is the biggest babysit item. Store frame vectors in the sidecar at analyze time, and embed only the query string through the same model loaded in-process (GGUF via llama-cpp-python, or a tiny ONNX/MLX text tower). Query cost drops to milliseconds and no subprocess exists. Rejected daemons stay rejected: nothing is left running.
### m02.6 YouTube/URL in, same card out, with the download hidden and the cache sized
Half of the daily videos are links. `framesift https://youtu.be/...` runs yt-dlp at a capped resolution (480p is enough for sampling at 128x72 and 768 px keyframes), picks the platform's own captions first and falls back to local ASR only when absent (zero ASR cost for most YouTube). A cache with a size cap and `framesift gc` keeps disk use from becoming a surprise bill.
### m02.7 Card first, always under a token budget, with a "what I could not tell" footer
The daily cost is per-turn tokens. The agent should receive a card whose size is fixed by a budget (for example 1.5k tokens text + one sheet) whatever the video length, with stat lines removed and deduped transcript cues, plus an honest footer: "no non-speech audio read; 3 segments have no keyframe change; ASR confidence low at 12:40-14:10". The agent then knows when to ask for `look`, instead of grepping a 207 KB storyboard.
### m02.8 Self-measuring: every run appends one line to a local log, and `framesift stats` shows what the daily habit really costs
Time per tier, failure reason, tokens of the card, whether the agent later called find/look. After two weeks Sam has real numbers on which feature earns its keep (the QA bench is synthetic). That is the cheap proof of the "runs every day" claim, and it deletes knobs that nobody uses.

## The provocation I would put to the group
The sensor is not a tool the agent calls but a thing that has already happened to the file by the time the agent opens it, so design the sidecar and its trigger first and the perception second.
